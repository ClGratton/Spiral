# Fab Asset Acquisition And Import Integration

Status: Accepted planning contract
Date: 2026-09-05

This contract defines the pre-demo Fab workflow requested for Spiral. It governs how the Editor hands off acquisition to Epic's supported surfaces, imports a user-selected local package, records provenance and license metadata, and proves the result in the actual Scene. `PLAN.md` alone controls implementation order and completion status.

## Evidence And Decision Levels

### Current official source claims

- Epic's [Purchasing and Downloading Assets](https://dev.epicgames.com/documentation/en-us/fab/purchasing-and-downloading-assets-in-fab) guide says Fab.com supports discovery, acquisition, library access, and direct download for applicable products. Adding a product to the library requires an Epic account sign-in; free products may also offer anonymous website download after the applicable EULA acknowledgement. A listing exposes its license, available formats, and technical details.
- Epic's [Fab in Launcher export guide](https://dev.epicgames.com/documentation/en-us/fab/exporting-assets-from-fab-in-launcher) says Fab in Launcher is available only on Windows and macOS. It supports local download plus exchange formats including FBX, glTF/GLB, OBJ, and USD/USDZ, and offers custom disk and local-socket export workflows. These launcher features are not evidence of a supported Linux launcher integration.
- Epic's [asset format requirements](https://dev.epicgames.com/documentation/en-us/fab/asset-file-format-and-structure-requirements-in-fab) list FBX, GLB, glTF, OBJ, USD, and USDZ among accepted exchange formats, but each listing controls which downloadable formats actually exist. UE-native content can require the UE integration or Launcher and is not an input to Spiral's portable importer.
- Epic's [licenses and pricing guide](https://dev.epicgames.com/documentation/en-us/fab/licenses-and-pricing-in-fab) distinguishes CC-BY, Fab Standard Personal, Fab Standard Professional, Personal Reference Only, and legacy UE Marketplace licensing. Standard Personal and Professional currently grant the same scope but use different eligibility/pricing tiers; Spiral records the user's acquisition-time declaration and never chooses a tier. `NoAI`, generated-with-AI, and legacy-license provenance are metadata to preserve, not permissions for the importer to adjudicate.
- The [Fab Standard License](https://www.fab.com/eula) summary permits use with compatible tools and incorporation into projects, but forbids redistributing the asset on a standalone basis. Reference-Only provides referenced content rather than source format. CC-BY content retains its own attribution requirement. The binding license text and the license attached to the acquired product remain authoritative.

These statements were rechecked against Epic's official pages on 2026-09-04. They do not establish a stable public entitlement/download API for Spiral, and they may change; implementation work must recheck the official pages before relying on them. No documented public marketplace REST/download API or CLI was found in the official material reviewed for this decision. UE Fab-plugin C++ classes are not a public marketplace-service contract.

### Project inference

Acquisition plumbing differs by host, but semantic import must not. Linux uses a user-controlled Fab.com session followed by explicit local-package selection. Windows may use the same website path or Epic's documented Fab-in-Launcher export to disk. Both yield one local input for the same importer, receipts, cooked formats, and project transaction. Spiral must not emulate an unavailable launcher, scrape the site, extract browser cookies, or infer entitlement from a URL.

### Amendment 2026-10-09: integrated Fab panel (user direction)

The project owner directed that the Editor must not hand acquisition to an external browser: Fab is to be integrated in the Editor so the user signs in, browses, and downloads in an embedded panel, the downloaded model appears as an Editor asset, and it can be dragged into the Scene. Dropping a downloaded `.zip`, `.glb`, `.gltf`, or package folder onto the Editor must import through the same path. This amendment supersedes decisions 1 and 3 below (external browser; no embedded profile) and the embedded-session wording in decision 3. Decisions 2 and 4-8 stand, with these clarifications:

- Spiral still never reads, copies, scrapes, or logs credentials, cookies, tokens, or payment state. The embedded browser engine owns its profile; Spiral code never opens that storage.
- There is still no private or reverse-engineered Fab API, no DOM scraping or script injection to build a catalogue, and no automated purchase, EULA acceptance, or license-tier choice. The panel shows Epic's own pages; the user performs every commerce action. Spiral observes only the engine's public download events for downloads the user started.
- The browser profile is app-owned, persistent, outside every project and repository, owner-only, never logged, and removable through a visible sign-out/clear-browser-data action. Persisting it is what makes login durable across Editor restarts.
- Navigation is restricted by an explicit policy (https only; Fab/Epic hosts plus the identity providers Epic's sign-in requires; popups and non-allowlisted top-level navigation denied). The feasibility gate must define the allowlist from observed sign-in flows rather than guess it.
- The browser engine, its dependency admission, sandbox mode, and packaging are chosen by a feasibility gate recorded in `Docs/DEPENDENCIES.md` before any code depends on it. Chromium Embedded Framework (CEF) in windowless/off-screen mode is the leading candidate because it behaves identically on Windows and Linux; WebKitGTK/Qt WebEngine (not identical across hosts) and proprietary embedded engines are the alternatives to be rejected or accepted on evidence.
- The panel is Editor-private (`Editor` owns it); `Engine` and `Sandbox` never link a browser engine. Dropped or downloaded packages enter the same Engine-owned snapshot, prepare/cook, receipt, and project-transaction authority, so the panel is an acquisition adapter and not a second importer.
- Not legal advice: the project owner owns the decision to embed Epic's web properties; this document does not assert Epic permits it.

Until the panel is accepted, drag-and-drop import of a user-acquired package is the interim acquisition-independent intake and is itself a required feature.

### Accepted project decision

The first supported integration requires Windows-and-Linux parity through one portable local-package importer:

1. (Superseded by the 2026-10-09 amendment for the Editor path.) On Linux the Editor opened the official Fab website in a normal user-controlled browser; the integrated panel replaces that. On Windows it may also accept a documented Fab-in-Launcher disk export. Search, sign-in, EULA acceptance, license/tier choice, purchase, export, and download remain visible human actions on Epic's surface.
2. Spiral receives only a path the user explicitly selects after download. It never reads browser profiles, cookies, passwords, session tokens, payment state, or private Fab endpoints and never automates checkout or EULA acceptance.
3. (Amended 2026-10-09.) Authentication durability belongs to the persistent app-owned embedded-browser profile described in the amendment above, or to the user's Fab-in-Launcher profile on Windows. Spiral never creates an incognito, temporary, or per-import profile, so closing or restarting the Editor does not itself require another sign-in. Windows and Linux retain separate host-local sessions, and Epic may still require reauthentication when its own session expires, is revoked, or account policy demands it. Spiral neither logs the user out nor claims to extend Epic's session lifetime.
4. The initial admitted content route is an archive or directory containing a glTF/GLB source plus texture payloads supported by the importer at implementation time. Unsupported engine-native, plugin, executable, script, encrypted, Reference-Only, or incomplete packages fail visibly; they are not silently converted by invoking another engine.
5. Import stages extraction, path and size validation, source hashing, glTF/texture validation, cooking, registry changes, and optional Scene assignment before one atomic project commit. Failure or cancellation preserves the prior registry, assets, Scene, and receipt set and removes owned staging files.
6. The durable receipt is versioned and records the canonical `https://www.fab.com/listings/<id>` URL confirmed by the user, publisher, selected product/version or download label when available, file format, declared license family and tier, required attribution text/link, source archive SHA-256, importer/cooker versions, resulting stable asset handles, and diagnostic acquisition time. A future UI may normalize a separately entered listing ID before validation, but the persisted identity is always the canonical URL. The source hash plus declared product/version/format—not path or timestamp—is the reimport identity. Fields unavailable from the package are explicit user-confirmed metadata, never guessed or scraped.
7. Duplicate import, same-product update, reimport, and source replacement are explicit outcomes. Same receipt identity and source hash reuse the accepted result; changed bytes create a new provenance generation and retain the old result until the replacement transaction succeeds.
8. Licensed raw downloads and extraction caches stay outside public engine artifacts by default and are ignored from source control unless the project owner deliberately chooses a license-compatible private storage policy. Spiral may ship cooked content only as incorporated project/game content under the user's applicable license; it does not claim to decide legal compliance. CC-BY attribution metadata must remain exportable into future packaging receipts.

The implementation is deliberately staged without weakening that final contract. Linux directory intake is the first independently verifiable hostile-input boundary. The next product milestone admits portable ZIP/image dependencies, shared semantic cooking, the project transaction, headed Linux/Vulkan import, and the first retained demo-scene benchmark on the available Linux host. Windows secure intake and full dependency/cook/Editor parity follow as explicit gates before cross-platform Fab completion. A checked Linux milestone therefore does not claim Windows behavior, and the later Windows gate must use the same shared semantic importer rather than creating a second one.

Windows Fab-in-Launcher disk export is an acquisition adapter in the first supported cross-platform feature, not a second importer. An optional explicit loopback-socket optimization and macOS support remain later adapters. Any socket path must be capability-gated, opt-in, authenticated to one user-visible import session, bounded in payload/path/size, and unable to mutate a project without the same preview and atomic commit.

## Ownership And Security Boundaries

- `Editor` owns the browser handoff, import preview, user-confirmed metadata, file picker, progress, cancellation, and optional Scene assignment.
- `Engine::Assets` owns package validation, safe extraction policy, semantic import/cooking, stable handles, provenance generations, and transactional publication. It does not own browser authentication or commerce.
- The external browser or documented Fab-in-Launcher profile owns login persistence. Spiral must reuse the ordinary host-local session without copying it into project or engine state. Any future public token-based integration requires a separate security decision and platform credential-vault storage with expiry, refresh, revocation, and explicit disconnect behavior; plaintext config, project files, receipts, and logs are forbidden credential stores.
- Existing glTF, material, texture, and registry contracts remain the only content authorities. Fab origin is provenance, not a special renderer path.
- Renderer and Scene consume normal cooked assets and stable handles; neither receives Fab URLs, credentials, archive paths, or license policy.
- Package input is hostile until validated. Reject every symlink/reparse point and hardlink, device, FIFO, socket, mount/device crossing, absolute/drive/UNC/parent-traversal path, backslash, empty/dot segment, colon/alternate stream, control byte, trailing dot/space, portable case-fold collision, unsupported nested archive, executable/script payload, excessive count/depth/path/segment/file/aggregate size, malformed encoding, and package change during hashing/import. The first dependency-free boundary accepts portable ASCII member names only; Unicode normalization is deferred until an explicit authority is admitted.
- Logs, crash reports, receipts, and automation output redact user paths when practical and never contain credentials, cookies, authorization headers, or browser storage.

### Immutable intake and identity

Linux directory intake inventories the tree descriptor-relatively, opens each regular file beneath a retained root with `openat`/`fstatat` no-follow semantics, compares file and mount identity before and after streaming copy plus SHA-256, and re-inventories the source before acceptance. It retains close-on-exec parent/snapshot descriptors, seals and rehashes the copied tree after the final callback, and cleans by exact device/inode identity even if the original staging pathname is replaced. A changed source fails with a stable changed-source diagnostic; the current `bool`/error API does not expose a typed status enum.

Windows intake source now provides the equivalent boundary with retained handles, protected current-user staging, parent-relative native opens, handle-native directory and stream enumeration, reparse-point rejection, stable file/volume identity and link-count checks, and exact-owned cleanup without a trust-bearing pathname reopen. Snapshot consumers use a retained-root streaming API that revalidates identity, size, and SHA-256; the stored DOS path is diagnostic only. A parent-path attack has two safe outcomes: if Windows permits the rename/replacement, retained streaming and cleanup remain bound to the original object; if live-handle sharing prevents the rename, the unchanged retained object remains authoritative and is cleaned exactly. Linux descriptors and Windows handles feed identical canonical names, byte hashes, glTF dependency validation, receipt identity, cooking, and project-transaction logic. Semantic parsing on both hosts reads only the private copied snapshot. This is source and Linux-regression evidence only until native MSVC and hosted Windows execution qualify the Win32 mechanism.

Directory/expanded defaults are bounded to 4,096 regular files, depth 16, 1,024-byte canonical paths, 255-byte segments, 1 GiB per expanded file, 8 GiB aggregate expanded bytes, and 64 MiB glTF JSON. The future archive adapter additionally limits compressed input to 4 GiB, per-entry expansion to `max(1 MiB, compressed * 100)`, and aggregate expansion to `max(16 MiB, compressed * 50)`. Arithmetic is overflow-checked and tests inject small policies to exercise exact boundaries. The initial ZIP profile admits only single-disk Store/Deflate; encrypted, split, executable, nested-archive, and Zip64 inputs remain rejected until separately qualified.

The canonical expanded-tree digest is domain-separated and hashes sorted canonical path, file size, and per-file SHA-256; timestamps and the user's local path are excluded. Fab identity has two levels:

- `streamId = SHA256("SpiralFabStreamV1\n" + canonical listing URL + "\n" + declared version/download label + "\n" + format token + "\n")`;
- `generationId = SHA256("SpiralFabGenerationV1\n" + streamId + "\n" + source SHA-256 + "\n" + expanded-tree SHA-256 + "\n")`.

Stable semantic asset handles take the first eight big-endian bytes of `SHA256("SpiralFabAssetV1\n" + streamId + "\n" + asset-type token + "\n" + semantic role + "\n")`, mapping zero to one. They derive from the stream, not the source digest. Exact duplicate bytes can therefore reuse a generation, while changed bytes prepare a new immutable cooked root without breaking Scene references. The published registry snapshot contains the generation-specific cooked root and source/watch policy. Older renderer snapshots retain their old root and must never resolve through the newest global handle-derived file. Generation directories are engine-created trusted cooked output; the current resolver foundation does not claim race-resistant containment or receipt-hash enforcement against arbitrary same-user tampering after publication. The later manifest transaction owns create-once publication and reload validation.

The versioned receipt records the declared identity and license fields, source and expanded-tree digests, importer/cooker versions, generation, semantic handles, generation-relative artifact paths and hashes, raw-source policy, and diagnostic acquisition time. It never stores the selected absolute source path. Missing or corrupt prior receipts, contradictory metadata, Reference-Only content, unconfirmed declarations, or CC-BY without attribution fail closed.

### Preparation and project commit

Package snapshotting, glTF/material/texture conversion, candidate registry/material/receipt construction, cooked generation creation, and optional Scene assignment are preparation. They do not mutate live state. The first truthful glTF profile is exactly one static renderable glTF/GLB root, triangles, baked node transform, UV0, one opaque metallic-roughness material, and admitted local textures. Remote/file URIs, escaping or percent-encoded traversal, skins, animation, morphs, compressed geometry, multiple materials, unsupported alpha/sampler combinations, and missing dependencies reject instead of silently degrading.

Cooked assets and complete project state are written to immutable transaction-owned generation directories. One atomically replaced project manifest is the sole commit pointer for the Scene, registry, materials, Fab receipts, and cooked generation. Cancellation is accepted through the pre-manifest boundary and removes only transaction-owned staging. After the manifest replacement, the result is committed rather than falsely reported as rolled back. Live state and one new renderer catalog are swapped only from the reload-validated committed candidate; a post-commit live-load failure is recovery-required and reloads the committed manifest.

### Browser engine decisions from the feasibility gate (2026-10-09, Linux spike)

A scratch spike (CEF 154.0.34, Chromium 154.0.8037.98, off-screen mode, software rendering, this Arch/Hyprland/XWayland host) established: the sandbox runs ON without a setuid helper through user namespaces, but a denied user-namespace sandbox is a fatal abort of the whole host process, so the Editor needs a preflight or process isolation before initializing it; `CefExecuteProcess` must run first in a separate helper executable (the Editor's `main()` is owned by the Engine entry point) and the helper calls `_exit` with its exit code; `root_cache_path` and `cache_path` must be canonical absolute paths or CEF silently falls back to in-memory storage; with `persist_session_cookies` a persistent profile keeps cookies across restarts without Spiral reading them; downloads the user starts are staged in a 0700 directory and `IsComplete()` is the completion edge; popups and non-allowlisted top-level navigations are denied; fab.com rendered without a bot or consent wall and the Epic sign-in page offered email, PSN, Xbox, Nintendo, Google, Steam, Disney, Apple, Facebook and LEGO without refusing embedded browsers; a 1080p BGRA frame copy costs about 0.4 ms, and Fab at 60 fps used about 17% of one core (hidden: 0.3%), so the panel caps at 30 fps and calls `WasHidden(true)` when not visible. Standard CEF builds lack H.264/AAC. Top-level navigation is limited to exact hosts `www.fab.com` and `www.epicgames.com`; identity-provider hosts are added only after the user observes each flow. Not verified: accelerated (dma-buf) painting, coexistence with GLFW and Vulkan in one process, Google/Apple/Facebook sign-in, anything after sign-in, keyring-backed cookie encryption (could raise a Spiral-attributed unlock prompt; `--password-store=basic` is the weaker fallback), Windows, macOS, and hosted CI. Chromium security rebuilds land frequently, so re-pinning the SHA-256 values in `Scripts/BrowserRuntimePins.env` needs a named owner and procedure. The wrapper must be built with the host compiler.

### CEF host library behavior (2026-10-09, Linux, headless-verified)

The adapter is a separate shared library loaded on demand: the Editor `dlopen`s `cef/libSpiralBrowserHost.so`, resolves the factory and destroy symbols, passes the ABI version and `sizeof(BrowserSurfaceConfig)`, and falls back to the null surface on a mismatch; it never `dlclose`s the library. CEF can be initialized once per process, so a failed initialization (including 'profile in use') is final until the Editor restarts, and sign-out deletes the profile after shutdown and requires a restart to sign in again. The adapter preflights `unshare(CLONE_NEWUSER)` in a forked child before initializing, uses headless ozone with software (SwiftShader) rendering, and has no OS clipboard or IME bridge under headless ozone (clipboard is process-internal until a bridge is built). The Editor shuts down by requesting close, pumping until closed, `Shutdown`, destroying the surface, and only then tearing down GLFW and the Vulkan device. For a ZIP the receipt's source SHA-256 is the archive's SHA-256; for a folder or a bare `.glb` it is the snapshot's expanded-tree SHA-256 (a bare `.glb` is first copied into a one-file staging directory). Receipts require a non-empty publisher. The controller's default cook staging root is `<project>/.fab-staging` and its package staging root is under the XDG cache directory.

### Implemented preparation profile and commit mechanism (2026-10-09, Linux)

The shared glTF/GLB profile implemented by `Engine::PrepareFabGltfPackage` is: one default (or sole) scene; every node-primitive instance baked into a single mesh artifact with node transforms in double precision, inverse-transpose normals, and swapped winding when the world determinant is negative; missing normals derived with the existing area-weighted rule; `TEXCOORD_0` required only when a texture is used; `COLOR_0` admitted only when all white; one opaque metallic-roughness material shared by every primitive (several distinct materials reject); base-colour/emissive textures sRGB and normal/ORM textures linear, with metallic-roughness and occlusion repacked into the single ORM slot (different source images must have equal size and sampler); PNG and JPEG decoded only through `DecodeCommonImage`; alpha forced opaque. Everything else in the rejection list above rejects with a stable error. Normal textures are cooked and bound but the production shader does not yet sample them and vertices carry no tangents; the demo records this as an explicit omission.

Identity rules fixed by the implementation: a semantic `LogicalPath` is the semantic role with its first `.` replaced by `/` (never a package file name) and the registry source path is `fab:<streamId>/<LogicalPath>`; a source replacement that adds or drops a texture role changes the stream's semantic asset set and classifies as a conflict that needs a new version label; for a directory or dropped non-archive input the receipt's source SHA-256 equals the snapshot's expanded-tree SHA-256 (a dropped bare `.glb` is first copied into a one-file snapshot), and for a ZIP it is the archive's SHA-256.

The project commit mechanism is `Engine::CommitProjectRevision` (manifest format 7 with `FabReceipts` and `ProjectRevision`): validate descriptor-relative paths, take a non-blocking project-root lock, compare-and-swap the manifest SHA-256 and require revision = previous + 1, hash-verify then publish the staged generation with no-replace directory rename (an existing final directory is adopted only if every artifact hash matches and nothing extra exists), create each revision file exclusively, replace the manifest atomically (the commit instant), then run the caller's reload validation, which reports commit-recovery-required on failure. Any failure before the pointer removes only what the transaction created. Opening a project runs a structural Fab validation (receipt/registry agreement, exact generation file set, no links, Fab materials load); Validate Project and commit run the full-hash level. Superseded generations are retained but not verified, and the structural level does not detect same-size byte flips (receipts hold no sizes). Non-Linux platforms return an explicit unsupported status until the Windows parity gate. The Editor must treat a commit as an undo barrier, load Fab materials through the immutable-material path (never as writable physical files), and set `ExpectedManifestSha256` from the exact manifest bytes read at open.

## Verification Contract

The accepted Linux directory-snapshot foundation covers minimal text glTF/GLB, missing/ambiguous/corrupt roots, absent or undersized external/GLB buffers, strict JSON, plain and percent-encoded traversal, root/child symlinks, hardlinks and special objects, portable case-fold duplicates, exact count/depth/path/segment/file/aggregate/JSON boundaries, unsupported payloads, changed-on-read input, every exposed cancellation point, final staged-tree tampering, staging-parent replacement, close-on-exec ownership, deterministic tree hashing, transactional output preservation, and exact-owned cleanup. Shared deterministic receipt/registry tests cover canonical serialization, independent identity vectors, license/attribution failure closure, duplicate/update/replacement classification, schema migration, watcher exclusion, atomic storage, and retained old/new rooted resolvers. These tests do not prove Windows intake, archives, image decoding, cooking, project commit, or Editor behavior.

Linux ZIP/image, prepare/cook, and project-transaction work must add the shared fixtures for role-mismatched textures, duplicate and identical reimport, changed-source replacement with old resolver continuity, corrupt prior state, atomic project commit, cancellation at every publication boundary, and save/reopen. Every failure must preserve prior project state and remove only transaction-owned staging. Windows foundation and feature parity later execute the equivalent reparse/link/volume/race/limit/cancellation/hash corpus plus those same portable fixtures natively under MSVC and in the focused hosted lane; they do not block truthful Linux-only acceptance.

The headed Linux gate runs first using the actual current Debug Editor and native Vulkan backend with Fab.com; its retained project then supplies the first complete scene benchmark. The headed Windows gate follows using the actual current Debug Editor and D3D12 backend with Fab.com or documented Fab-in-Launcher disk export. In both, the user alone completes sign-in, EULA, acquisition, and download/export; the agent then resumes automatically, imports through the same real Editor controller, confirms receipt/stable assets, assigns the mesh/material, saves, closes, reopens, and verifies the same asset visibly renders. Closing/reopening Spiral and starting a second acquisition must reuse an externally valid ordinary browser/Launcher session without a new Spiral-caused login prompt; an Epic-required expired/revoked-session prompt is not an engine failure. Identical reimport must reuse identity, and one controlled invalid package must fail without changing the accepted Scene.

Each gate records the exact Editor executable, backend/device, canonical listing URL, selected format, source hash, declared license/tier/attribution state, resulting handles, save/reopen result, and visible/capture evidence. It does not record credentials or prove Epic entitlement beyond the user's acquisition action. Automated fixtures do not substitute for one actual Fab-acquired asset on each required platform, and a browser/Launcher download alone does not prove Editor integration.

## Explicit Non-Goals For The First Integration

- No private or reverse-engineered Fab API, headless login, cookie reuse, automated purchasing, or background entitlement polling.
- No Linux claim for Fab in Launcher, and no Wine/Proton dependency.
- No direct import of Unreal `.uasset`, `.uproject`, or `.uplugin` packages.
- No marketplace publishing, resale, license adjudication, automatic update service, or standalone redistribution of source assets.
- No new renderer-only Fab path; the demo Scene must exercise ordinary Spiral asset, material, Scene, and renderer contracts.
